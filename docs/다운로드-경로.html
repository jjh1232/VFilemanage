다운로드 경로

받기 버튼을 누르면 96MB 파일이 어디서 어떻게 오는가. 페이지는 Cloudflare에, 파일은 GitHub에 있고 그 사이를 잇는 건 링크 두 줄이 전부다.

왜 둘로 나눴나

파일을 페이지와 같은 곳에 두지 않는다. 정적 호스팅은 대개 파일 하나에 25MB 안팎의 제한이 있어 96MB짜리 exe가 애초에 안 올라가고, 올라가더라도 내려받는 트래픽이 전부 비용이 된다.

GitHub Releases는 파일당 2GB까지 받아 주고, 공개 저장소면 트래픽 요금이 없다. 그래서 페이지는 43KB, 파일은 231MB로 갈라 두고 링크로만 잇는다.

연결 고리는 이 두 줄

페이지에서 다운로드에 관여하는 코드는 이것뿐이다. 자바스크립트도, 다운로드 처리기도 없다.

주소 형태가 핵심이다. releases/download/…는 파일을 내려주는 주소고, releases/tag/v1.0.0은 사람이 보는 릴리스 화면이다. 후자를 걸면 방문자가 GitHub 페이지로 튕겨 나가 거기서 파일을 다시 찾아야 한다.

누르면 일어나는 일

방문자는 페이지를 떠나지 않는다. 주소창도 그대로다. 실제로 측정한 응답이다.

클릭
github.com/jjh1232/VFilemanage/releases/download/v1.0.0/VFilemanage-1.0.0-setup.exe
페이지에 적힌 그대로의 주소
302
release-assets.githubusercontent.com/…
GitHub이 자기 CDN으로 넘긴다. 방문자는 못 느낀다
200
Content-Type: application/octet-stream
Content-Disposition: attachment; filename=VFilemanage-1.0.0-setup.exe
이 헤더가 전부를 결정한다. attachment가 붙으면 브라우저는 그 주소를 열지 않고 저장한다 — 그래서 페이지 이동 없이 다운로드 표시만 뜬다

Worker는 여기에 관여하지 않는다

이 도구에도 Cloudflare Worker가 있지만 다운로드와는 무관하다. Worker가 하는 일은 두 가지뿐이다.

worker/index.js
// 1. 자산 경로에서 도구 접두사를 뗀다
//    /vfile/ko/ → /ko/   (site/ 안이 그대로 사이트라서)
const path = url.pathname.slice(PREFIX.length) || '/';

// 2. 도구 루트는 브라우저 언어로 갈라 보낸다
if (path === '/') {
  const lang = pickLang(request.headers.get('accept-language'));
  return new Response(null, {
    status: 302,                        // 301이면 브라우저가 영구 캐시해
    headers: {                          // 방문자가 언어를 되돌릴 수 없다
      location: `${PREFIX}/${lang}/`,
      'cache-control': 'no-store',     // 없으면 엣지가 첫 방문자의
      vary: 'Accept-Language',          // 언어를 전원에게 준다
    },
  });
}

다운로드 링크는 github.com을 향한 절대 URL이라 브라우저가 곧장 그리로 간다. 우리 도메인을 거치지 않으니 Worker도, Cloudflare 대역폭도 쓰지 않는다.

버전을 올릴 때 고쳐야 하는 곳

파일명에 버전이 박혀 있어서 v1.0.1을 내면 링크가 전부 바뀐다. 세 언어판 중 한 장만 옛 버전을 가리켜도 그 언어 방문자만 404를 받고, 다른 언어로 보는 사람에게는 아무 일도 일어나지 않아 눈으로는 못 잡는다.

고칠 곳무엇을
site/ko|en|ja/index.html다운로드 링크 2개, 표시 용량, SHA-256 2개 — 언어판마다
test/links.jsVERSION 상수
site/sitemap.xmllastmod

그래서 검사를 자동화해 뒀다. 배포 전에 npm run deploy가 먼저 이걸 돌리고, 실패하면 배포가 멈춘다.

test/links.js
// 두 자산이 정확한 버전을 가리키는지
for (const asset of ASSETS) {
  if (!html.includes(RELEASE_BASE + asset)) {
    bad(rel, `다운로드 링크에 ${asset} 가 없다 (버전 v${VERSION})`);
  }
}

// 옛 버전이 섞여 있으면 그 언어만 404 가 된다
for (const m of html.matchAll(/releases\/download\/v([\d.]+)\//g)) {
  if (m[1] !== VERSION) bad(rel, `옛 버전 v${m[1]} 가 남아 있다`);
}

릴리스를 올리기 전에 눌러보려면

링크가 GitHub을 가리키므로, 릴리스를 올리기 전에는 버튼이 404다. 그렇다고 테스트하려고 페이지의 주소를 로컬로 바꿔 두면 그 상태로 배포될 위험이 생긴다.

그래서 파일은 그대로 두고, 서버가 내보내는 순간에만 주소를 바꿔치기한다.

로컬 미리보기 서버
// /dl/ 요청이 오면 실제 빌드 산출물을 내려준다
if (rel.startsWith('/dl/')) {
  const name = path.basename(rel.slice(4));   // 경로 조작 차단
  const full = path.join(RELEASE, name);
  const { size } = fs.statSync(full);

  res.writeHead(200, {
    'Content-Type': 'application/octet-stream',
    'Content-Length': size,
    'Content-Disposition': `attachment; filename="${name}"`,  // 진짜 배포처럼
  });
  fs.createReadStream(full).pipe(res);   // 96MB라 통째로 읽으면 안 된다
  return;
}

// HTML을 내보낼 때만 GitHub 주소를 로컬로 돌린다.
// 디스크의 index.html은 배포용 그대로 남는다
if (ext === '.html') {
  const html = fs.readFileSync(full, 'utf8').split(GH).join('/dl/');
  res.end(html);
}

서명이 없어서 생기는 일

"Windows에서 PC를 보호했습니다"

코드 서명 인증서가 없으면 SmartScreen이 처음 보는 프로그램으로 판단해 파란 경고를 띄운다. 기본 버튼이 실행 안 함이라 여기서 이탈이 제일 많이 난다.

인증서를 사지 않을 거라면 페이지에서 넘어가는 방법을 반드시 안내해야 한다. 그게 없으면 대부분 여기서 포기한다.

대신 파일이 진짜인지 확인할 방법을 함께 준다. 페이지에 적힌 SHA-256은 실제 배포 파일에서 뽑아 대조한 값이다.

Get-FileHash .\VFilemanage-1.0.0-setup.exe -Algorithm SHA256 | Format-List

setup  70DAC5D312BF1176B8825FC7A08AFB591926A487F90AFF6B6EE06165BB2F8108
zip    1866C77F8D124DFD0237DBA421B18D8AD91F3C080493DB59577494FA884C3932

배포한 뒤에는 페이지에서 링크와 체크섬을 긁어 그대로 받아 대조해 확인했다. 방문자가 겪는 경로 그대로를 밟는 검증이라, 링크가 살아 있는지와 값이 맞는지를 한 번에 잡는다.

  • 첫 배포 때 이 검증이 사고를 잡았다. 업로드된 파일이 %APPDATA%\react-parcel을 쓰던 옛 빌드였는데, 해시가 안 맞아 드러났다. 그대로 뒀으면 받아간 사람들 PC에 옛 이름 폴더가 만들어져 되돌릴 수 없었다.
